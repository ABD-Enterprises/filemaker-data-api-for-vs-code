# ADR-0005: The @filemaker chat participant

- Status: Accepted (addendum to ADR-0004; all 15 standing rules of ADR-0004 apply unchanged).
- Date: 2026-10-18

## Context

ADR-0004 gave AI clients two transports to one tool core (`AiToolService`): VS Code language-model tools and an MCP server. The Chat view in VS Code also lets an extension contribute a **chat participant**, a handler a user addresses with `@name` and slash commands. A participant is a third front end to the same core. It must add no policy and no capability.

## Decision

Add `@filemaker` (`vscode.chat.createChatParticipant`) with slash commands `/layouts`, `/describe LAYOUT`, `/find LAYOUT criteria`, `/explain CODE` and `/help`. The first version is **read only** and has **no free-form chat**: text without a command gets the command list.

Code: `extension/src/ai/chat/` (`chatParticipant.ts` handler and logic, `chatText.ts` rendering, `chatPrompt.ts` the one model prompt, `chatRegistration.ts` the VS Code glue). The handler calls `AiToolService.invoke(name, input, { signal, client: 'chat participant' })` and nothing else. It does not call `vscode.lm.invokeTool` (see "API choices").

### Behaviour

| Command                 | What it does                                                                                                                                                                                                                                                         | Tools it calls                                             |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| `/layouts`              | Lists layout names as the core returns them (allowlisted names; others shown as unusable)                                                                                                                                                                            | `fm_list_layouts`                                          |
| `/describe LAYOUT`      | Field names and types of one layout; value lists are not exposed by the tools, and the answer says so                                                                                                                                                                | `fm_describe_layout`                                       |
| `/find LAYOUT criteria` | `Field=value; Other==value` with known fields is turned into a request by the extension. Anything else goes to the language model the user chose in the chat; the model gets one tool and must call it. The host then validates the request exactly as the tool does | `fm_list_layouts`, `fm_describe_layout`, `fm_find_records` |
| `/explain CODE`         | The shared FileMaker error table; without a code it uses the last FileMaker error code seen by this participant                                                                                                                                                      | `fm_explain_error`                                         |
| `/help`                 | Static text                                                                                                                                                                                                                                                          | none                                                       |

Rules the participant follows on top of ADR-0004:

1. **All policy is the core's.** `filemaker.ai.enabled` (user scope), the connection chosen for AI, the connection's `aiAccess`, trust, offline mode, the kill switch, the `ai` feature switch and enterprise policy, layout approval dialogs, hidden fields, the 50-record, 500-record and 30-call limits all apply because the call goes through `invoke`. A test runs the real core behind the participant for every gate.
2. **No write or script capability.** The names the participant ever passes to `invoke` are `fm_list_layouts`, `fm_describe_layout`, `fm_find_records` and `fm_explain_error`. The only tool offered to a model is `fm_find_records`, in `LanguageModelChatToolMode.Required`, whatever `allowWrites` and `allowScripts` say. A model that asks for any other tool (a write tool included) gets nothing run. The manifest adds no command and no tool.
3. **The model never sees record data or credentials.** `/find` sends the model the layout name, the field names of that layout (hidden fields removed by the core) and the user's own words, as one JSON string after fixed instructions. No profile name, server address, user name or token goes into any prompt. Record values go from the core to the screen and are never sent to the model by this participant.
4. **The layout is the user's choice, and the size is capped.** The `layout` of the model's request is overwritten with the layout the user named, and its `limit` is set to at most 10 (the size of a `Field=value` search). Everything else in the request is validated by the core (closed grammar, at most 5 requests, known fields only, `additionalProperties: false`).
5. **Rendering is structural.** Chat responses are Markdown and can carry links, images, HTML and `command:` links. Everything from a database or a model (layout, field and record text, error text, a policy reason) is written only inside a fenced code block. The fence is one backtick longer than the longest backtick run in the text, so the text cannot close it, and each value is a single line with control, format and separator characters written as `\uXXXX` and a length cap. Outside fences there are only constants of the extension and numbers. `stream.markdown` always gets a plain string, never a `MarkdownString`, so `isTrusted` is never set and no command link can run. No images are emitted. Every part written to the response ends with a blank line (VS Code may join parts with nothing between them, and text glued to a closing fence would leave the block open; an independent review found this). Output is capped at 12,000 characters (a cut closes any open fence), at most 20 records and 40 fields per record are shown, values are cut at 200 characters, and a request longer than 1,000 characters is refused.
6. **Text the model writes is discarded.** Only a tool call can lead to anything, and it is validated. Model error text is scrubbed (`redactString`, `scrubGenericText`) before it is shown; an unexpected exception shows a fixed message.
7. **Off means off, with a way back.** When `filemaker.ai.enabled` is off the participant says so, lists the three steps, and offers a button for the constant command `workbench.action.openGlobalSettings` with the constant query `filemaker.ai`. The kill switch gets a button for the existing kill-switch command (which asks before switching on). Other reasons (policy, untrusted workspace, offline) are shown as fenced text with no button. No command or argument is ever built from data.
8. **Untrusted workspaces.** The participant is registered (the manifest declares it, and an unregistered declared participant would fail confusingly) but every request is refused by the core with the untrusted-workspace reason.
9. **Audit and telemetry.** Every core call carries the claimed client name `chat participant`, so **Show AI Activity** distinguishes it. No telemetry is added.

### API choices and versions

Checked on 2026-10-18 against the VS Code API reference, the chat guide, and `vscode.d.ts` of `release/1.96` and `main`.

| API                                                                                                                                                             | Stable since                                                                                                                 | Used                                                                                                                                                                                                                                                    |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `contributes.chatParticipants` (`id`, `name`, `fullName`, `description`, `isSticky`, `commands`)                                                                | release not confirmed from the docs (the guide gives no version); VS Code ignores an unknown contribution on an older editor | yes                                                                                                                                                                                                                                                     |
| `vscode.chat.createChatParticipant`, `ChatRequest` (`command`, `prompt`, `model`), `ChatResponseStream` (`markdown`, `button`, `progress`)                      | in `@types/vscode` 1.96                                                                                                      | yes                                                                                                                                                                                                                                                     |
| `ChatRequest.model.sendRequest` with `tools` and `toolMode`, `LanguageModelChatToolMode.Required`, `LanguageModelToolCallPart`, `LanguageModelChatMessage.User` | in `@types/vscode` 1.96                                                                                                      | yes                                                                                                                                                                                                                                                     |
| `vscode.lm.invokeTool`, `ChatRequest.toolInvocationToken`                                                                                                       | in 1.96                                                                                                                      | **no**: the participant calls `AiToolService.invoke` directly, so it controls the tool list and the client name, and the Chat UI does not need to show a tool-confirmation (which can be set to always allow, so it is not a control, ADR-0004 phase 2) |
| `vscode.lm.registerLanguageModelChatProvider`                                                                                                                   | 1.104 (not in `@types/vscode` 1.96)                                                                                          | **tests only**: the end-to-end helper extension registers a fake model if the editor has it                                                                                                                                                             |
| `onChatParticipant:<id>` activation event                                                                                                                       | documented in the activation events reference                                                                                | yes (the extension already activates at start-up)                                                                                                                                                                                                       |

The engine floor stays `^1.96.0` and `@types/vscode` stays `~1.96.0`: nothing the participant needs is proposed or newer. On an editor without `vscode.chat.createChatParticipant` the participant is not created (feature-detected, `getChatApi()`), and `LanguageModelChatToolMode` is read with optional chaining. I could not confirm from the docs the exact VS Code release in which each API went stable; the statement above rests on the 1.96 type definitions containing them as non-proposed declarations. The e2e run used the current stable VS Code (see the PR).

## Threat model delta

| Threat                                                                                                                              | Mitigation                                                                                                                                                                                                                                                                                                       |
| ----------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Hostile layout, field, record or error text injects Markdown (links, images, HTML, `command:` URIs, a fence breakout) into the chat | Untrusted text only inside an unbreakable fence, one escaped line per value, plain-string `markdown()`, no images, caps; corpus test over every renderer; mutation-checked                                                                                                                                       |
| Hostile text steers the model into a write, a script or another tool                                                                | The model gets one read tool in required mode; anything else is discarded unrun; the layout is overwritten; the core validates; the core refuses writes unless the user enabled them, and the participant never lists them anyway                                                                                |
| The model is given data it should not have                                                                                          | No record values, credentials, server address or profile fields are sent; field names pass through the core's hidden-field filter. Field names are still an uncontrolled text channel (ADR-0004 rule 14) and a hostile field name reaches the model; the structural controls above are the defence               |
| Participant widens what AI may do                                                                                                   | All gates are the core's, the call is `invoke`, and tests run the real core for every gate (settings, kill switch, feature switch, enterprise policy, trust, offline mode, connection access, layout approval, hidden fields)                                                                                    |
| A command link built from data                                                                                                      | The only buttons are two constant commands (open the AI settings, the kill switch); no argument comes from data                                                                                                                                                                                                  |
| User confuses the participant with a sandbox                                                                                        | `/help` and the user guide say what is sent to the model (layout and field names and the user's words) and that record values are shown only in the chat                                                                                                                                                         |
| Residual: the chat history holds record values                                                                                      | Record values rendered in the Chat view stay in the chat history of VS Code and may be sent to the model by later free-form chat messages of other participants or by Copilot's own context. The user guide says so; this is the same class of residual risk as ADR-0004's "data in a model's context can leave" |

## Consequences

- One more transport, no new policy: a change to the tool core (a new tool, a new gate) reaches the participant without code here, except that a new read tool is not offered to it until it is added deliberately.
- Every request in the Chat view is a few tool calls (`/find` is three), so it counts against the 30 calls a minute.
- `/find` needs a model only for plain-language criteria; `Field=value` works with no model.

## Not done

- No free-form questions and no multi-turn tool loop: a loop would feed record values back to the model.
- No write, edit, delete or script commands. A later version needs its own review.
- No `followupProvider`, no `iconPath`, no `disambiguation` routing (it would let VS Code route unrelated chats to the participant).
- Real language-model behaviour (does a given model call the tool correctly) is not tested; only the test double is.
